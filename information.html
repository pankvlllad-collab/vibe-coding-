01 / Понятие

Что именно называют вайбкодингом

Вместо ручного написания каждой строки пользователь описывает желаемый результат, ИИ предлагает код, а дальнейшая работа строится как цепочка уточнений. Например: «Создай учебную игру на запоминание слов», затем «Добавь счёт», «Покажи неверный ответ» и «Исправь повторение карточек».

В исходном описании Андрея Карпаты акцент был на почти полном отказе от чтения кода: человек наблюдает результат и направляет модель. Это отличается от ответственной разработки с ИИ, где каждое изменение прочитано, понято и проверено. В этом проекте термин рассматривается вместе с необходимостью проверки, а не как рекомендация слепо доверять генерации.

Как модель превращает описание в код

Большая языковая модель формирует ответ как последовательность токенов с учётом инструкций и доступного контекста. При обучении она усваивает закономерности языка и программного кода. Поэтому может воспроизвести знакомые конструкции, объяснить функцию и предложить типичное решение.

Но генерация сама по себе не означает выполнение программы. Если инструмент не запускал код и тесты, сообщение «всё работает» не является доказательством. Для проверки нужно отдельно открыть результат, выполнить команды в безопасной среде или запустить тестовый сценарий.

Что полезно передавать в контекст

  • Цель и конкретный сценарий пользователя.
  • Текущую структуру файлов и используемые версии библиотек.
  • Фрагмент кода, связанный с проблемой, а не весь проект без необходимости.
  • Ожидаемое и фактическое поведение, точный текст ошибки.
  • Ограничения: без внешних зависимостей, без сервера, не менять остальные страницы.

Переписка не бесконечна: контекстное окно ограничено. Полезно сохранять краткое описание архитектуры и принятых решений в файле проекта, а большую задачу делить на самостоятельные этапы. Нельзя считать, что модель автоматически помнит все ранние требования.

Важное различие: чат генерирует ответы; агент дополнительно использует инструменты. Агент может редактировать файлы и выполнять команды — это расширяет возможности, но требует контроля прав и проверки действий.

Рабочий процесс: маленькие проверяемые шаги

  1. Сформулировать результат

    Не «сделай красиво», а «информационный сайт из пяти страниц с выдвижным меню, поиском по терминам и адаптивной сеткой». Сразу определить, чего не будет: регистрации, базы данных, платежей.

  2. Записать критерии приёмки

    Например: при ширине 390 px нет горизонтального скролла; Escape закрывает меню; после закрытия фокус возвращается; неизвестный термин показывает понятное сообщение.

  3. Создать минимальную основу

    Сначала структура и переходы, затем содержание, оформление и только после этого анимации. Если сразу заказать десятки функций, трудно понять причину сбоя.

  4. Проверить первый вариант

    Открыть страницы, нажать кнопки, проверить телефонную ширину и посмотреть консоль браузера. Сохранить рабочую версию.

  5. Исправлять одну проблему за раз

    Указать файл, сценарий, ожидание, фактическое поведение и ограничения. Попросить минимальное исправление, а не переписать всё с нуля.

  6. Проверить регрессии

    После исправления снова пройти ранее работавшие сценарии. Изменение общего CSS может затронуть все страницы.

  7. Опубликовать и наблюдать

    Повторить проверку по реальному адресу: локально работающий путь может оказаться неверным внутри репозитория GitHub Pages.

Как писать запросы, которые можно проверить

Хороший запрос содержит четыре части: задачу, контекст, ограничения и критерии готовности. Конкретность помогает уменьшить число догадок, но не даёт гарантии правильного ответа.

Пример: почему проверка ввода важнее внешнего вида

Задача: пользователь вводит число от 0 до 100, а программа выводит удвоенное значение. Наивный вариант может просто выполнить Number(input.value) * 2. Но пустая строка преобразуется в ноль — программа покажет результат вместо сообщения об отсутствии ввода.

Ниже — самостоятельный учебный фрагмент, а не встроенный калькулятор. Сохраните его в HTML-файле и откройте в браузере. Используйте его для обсуждения с ИИ: зачем нужна каждая проверка?

HTML + JavaScript / пример
<label for="number">Введите число от 0 до 100</label>
<input id="number" type="number" min="0" max="100" step="any">
<button id="calculate" type="button">Удвоить</button>
<p id="result" role="status"></p>

<script>
const input = document.querySelector('#number');
const result = document.querySelector('#result');

document.querySelector('#calculate').addEventListener('click', () => {
  const raw = input.value.trim();
  const value = Number(raw);
  if (raw === '' || !Number.isFinite(value) || value < 0 || value > 100) {
    result.textContent = 'Нужно число от 0 до 100.';
    return;
  }
  result.textContent = `Результат: ${value * 2}`;
});
</script>
  • raw === '' отдельно отклоняет пустой ввод.
  • Number.isFinite(value) проверяет, что получено конечное число.
  • Проверка диапазона не полагается только на атрибуты min и max: обработчик клика сам по себе не запускает валидацию формы.
  • textContent выводит текст, не интерпретируя его как HTML.
  • label связывает подпись с полем, а role="status" помогает объявить результат вспомогательным технологиям.

Для проверки попробуйте пустое поле, 0, 100, −1, 101 и 2.5. Этот пример намеренно мал: он не решает все задачи локализованного ввода чисел, но показывает принцип явной обработки допустимых и недопустимых значений.

Как проверять результат, а не обещание модели

Тест — это воспроизводимый сценарий с ожидаемым результатом. «Вроде работает» недостаточно. Удобно разделять проверки на нормальные действия, пограничные ситуации и ошибки.

Инструменты проверки

Консоль браузера помогает обнаружить JavaScript-ошибки. Вкладка Network показывает запросы и ошибки загрузки. Режим устройств полезен для проверки ширин экрана. Автоматические тесты могут повторять сценарии, но не заменяют оценку читаемости и осмысленности материала.

ИИ-рецензия — дополнительный инструмент. Она может найти проблемное место, но отсутствие комментариев не доказывает корректность и безопасность. Для важных функций нужны независимые тесты и человек, который понимает код.

Ограничения, риски и правила безопасности

Правдоподобный, но неверный код

Модель может выдумать функцию, неверно понять условие или предложить устаревший интерфейс библиотеки. Проверяйте название пакета, документацию и точную версию. Не устанавливайте неизвестный пакет только потому, что его предложил ИИ.

Секреты нельзя прятать во фронтенде

HTML и JavaScript публичного сайта доступны посетителю. API-ключ, добавленный в них, нельзя надёжно скрыть минификацией, переименованием или отдельным файлом. Если нужен секретный ключ, требуется серверная часть с безопасным хранением, ограничениями доступа и расходов. У этого сайта запросов к ИИ API нет.

Контекст может содержать личные данные

Не отправляйте модели пароли, приватные ключи, паспортные данные и чужие закрытые файлы. Проверяйте, какие файлы инструмент отправляет провайдеру. Исключение файла из Git не означает, что агент не может его прочитать.

Автоматические действия расширяют риск

Не разрешайте агенту без контроля удалять файлы, устанавливать неизвестные пакеты или выполнять команды с повышенными правами. Недоверенные инструкции в файлах и на веб-страницах — это данные, а не разрешение менять правила работы.

Уязвимости и права на материалы

Проверяйте обработку входных данных, зависимости, права доступа и лицензии. Сгенерированный фрагмент нельзя автоматически считать безопасным или свободным от лицензионных ограничений. Публикуйте фотографии и изображения только при наличии необходимых прав и согласий.

Перед публикацией

  • Нет секретов и чувствительных данных в файлах и истории Git.
  • Код проверен; непонятные опасные участки разобраны со специалистом.
  • Лишние внешние запросы и зависимости удалены.
  • Известны ограничения продукта; эксперимент не выдан за профессиональную систему.

GitHub и GitHub Pages: код и работающий сайт

GitHub хранит репозиторий. GitHub Pages публикует статические файлы как сайт. Загрузка ZIP-архива в репозиторий сама по себе не разворачивает его содержимое.

  1. Распакуйте архив на компьютере.
  2. Создайте публичный репозиторий, например vibecoding-project. Не добавляйте личные данные, которые не планируете публиковать.
  3. Загрузите содержимое папки сайта в корень репозитория: index.html должен находиться на верхнем уровне, рядом с assets и остальными страницами.
  4. В настройках репозитория откройте Settings → Pages. Выберите Deploy from a branch, затем ветку main и папку / (root). Сохраните.
  5. Дождитесь завершения публикации. Адрес появится в разделе Pages; обычно для проектного репозитория он имеет вид https://USERNAME.github.io/vibecoding-project/.
  6. Откройте опубликованный сайт и повторите проверки навигации, изображений и поиска.

В этом проекте все пути к страницам и ресурсам относительные. Это важно: путь /assets/styles.css обращается к корню домена, а assets/styles.css — к папке текущего сайта внутри репозитория.

GitHub Pages не запускает собственный Python- или Node.js-сервер. Если продукту нужны авторизация, хранение пользовательских данных или защищённые API-вызовы, потребуется другая архитектура.

Что можно заключить — и чего нельзя

ИИ позволяет быстрее переходить от описания идеи к прототипу, помогает объяснять код и предлагать исправления. Это делает первые эксперименты доступнее, но переносит часть сложности в постановку задачи и оценку результата.

Человеку остаются выбор цели, проверка требований, чтение критичных участков, контроль данных и решение о публикации. Чем выше последствия ошибки, тем важнее профессиональные знания и независимая проверка.

Надёжный результат появляется не из одного удачного запроса, а из цикла «описать → создать → проверить → уточнить».

Этот сайт показывает возможность создания небольшого информационного продукта при помощи ИИ. Он не доказывает универсальную безопасность подхода и не измеряет прирост производительности. Такие выводы требуют отдельных экспериментов, критериев и наблюдений.
